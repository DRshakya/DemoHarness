What is the Harness?

Simple definition

The harness is a ready-made folder of rules, helpers, and AI assistants that makes sure tests are written the right way every time. It does not contain any app code. You bring the app; the harness brings the guardrails.

Think of it as three levels stacked on top of each other:

  • Level 1 — Playwright: The tool that actually runs the tests. You do not touch this layer.
  • Level 2 — The Harness (this repo): The AI assistants, the rules, and the automatic checks that make sure tests are written correctly.
  • Level 3 — Your Project: The only thing you write. A short description of your app and a list of things that need to be tested.
To plug in a new project: Copy the template, fill in your project name, run three commands, then run npm run verify. If it passes with zero tests — you are ready to start.
Example — setting up a new project
cp harness/profiles/projects/_template.json harness/profiles/projects/my-app.json
# Fill in the name and settings inside my-app.json, then:
npm run harness:compose
npm run harness:sync
npm run harness:check
npm run verify
# Expected output: "Running 0 tests using 0 workers" — this is correct

How the files connect

Every file passes information in one direction — from settings all the way to tests. Tests can never skip a level and grab settings directly.

playwright/configs/**            ← button names, page addresses, constants
        ↓
playwright/support/helpers/**    ← steps like "log in", "fill form", "check result"
        ↓
playwright/fixtures/base.fixture.ts  ← makes helpers available to tests
        ↓
playwright/tests/**              ← the actual test — just calls the steps above

Hooks

Simple definition

A hook is a small script that runs automatically at certain moments — before you write a file, after you write a file, or when you send a message. If something is wrong, the hook stops the action and tells you the problem before anything gets saved.

There are four moments when hooks can run:

  • When you send a message — checks before the AI starts working
  • Before a file is saved — checks the file before it touches the disk
  • After a file is saved — double-checks the saved file
  • When the AI finishes — shows a reminder checklist
You do not set up hooks manually. They are turned on automatically when you run npm run harness:sync.
Runs when you send a message harness-config-gate.mjs

What it does: Before the AI does any work, this hook checks that your project setup is complete. If you have not filled in your project details yet, the whole message is stopped and you see a setup guide instead.

Why it matters: Without a complete project profile, the AI would write tests for the wrong app or with the wrong settings.

What happens without a complete profile
You: "Write a test for the login page"
Hook: ❌ Project profile is incomplete.
      Fill in harness/profiles/projects/my-app.json
      then run: npm run harness:compose && npm run harness:sync
What happens with a complete profile
You: "Write a test for the login page"
Hook: ✅ Profile OK — AI starts working
Runs when you send a message prompt-duplication-guard.mjs

What it does: When you ask the AI to create something new (a test, a helper, a selector), this hook automatically adds a reminder: "Search first — does this already exist?" The AI must search for the exact text before writing anything new.

Why it matters: The same button selector could already exist in a config file. Two copies of the same thing mean double the work when the app changes.

Example — what the hook injects into your message
You said: "Add a helper for the checkout button"

Hook injects: "Before writing anything — search playwright/configs/**
and playwright/support/helpers/** for the exact selector value.
If it exists anywhere, reuse it instead of creating a new file."
Runs before a file is saved pre-validate-playwright-rules.mjs

What it does: Before any file is saved, this hook reads its content and checks it against all the hard rules. If it finds a problem, the file is never saved — the AI gets a clear error message.

Why it matters: Stopping a bad file before it is saved is better than finding the problem later in a code review.

AI tries to save a file with a hard-coded selector
// AI tries to write this to disk:
await page.click('[data-testid="login-btn"]');

Pre-write hook: ❌ BLOCKED — no-hardcoded-selector rule violated.
               Use a constant from playwright/configs/ui/** instead.
File with a config constant passes
import { LOGIN_BTN } from '../configs/ui/auth.selectors';
await page.click(LOGIN_BTN);

Pre-write hook: ✅ No violations — file saved
Runs after a file is saved validate-playwright-rules.mjs

What it does: Right after a file is saved, this hook checks it again. It also works in your CI pipeline — you can run it against all files that changed in a pull request.

Why it matters: Catches anything that slipped through, and works as the final check in CI for code written by humans too.

Running in CI on a pull request
node .claude/hooks/validate-playwright-rules.mjs --base-ref main
# Checks every changed .ts file in playwright/ against all rules
# Exit code 1 = violations found, PR blocked
# Exit code 0 = all clean
Runs when the AI finishes session-end-reminder.mjs

What it does: When the AI is done, if it touched any test files, this hook prints a checklist of things the QA reviewer will check. It reminds you to collect the test run output before asking for a review.

Why it matters: Without the checklist, it is easy to forget to run the tests or collect the lint output. The QA gate needs that evidence to give a verdict.

Example reminder printed at the end of a session
📋 Session touched test code. Before requesting a gate review, collect:

  ☐ npm test output (all tests passing)
  ☐ npm run lint output (no errors)
  ☐ npx tsc --noEmit output (no type errors)
  ☐ npm run evidence:build output

This is a reminder only — hooks and CI are the real enforcement.

Agents

Simple definition

An agent is an AI assistant that has one specific job. Each agent knows what it is allowed to do and what it is not. They do not overlap. The person who writes the test cannot also be the person who approves it — the same idea applies here.

There are 7 agents. Each one owns exactly one of the 9 steps. Giving a job to the wrong agent — for example, asking the reviewer to also write the test — breaks the checks that keep the process trustworthy.

Always start with project-bootstrapper when working on a new project or feature. Do not ask playwright-test-automation to write until a requirement is marked active.
GATHER project-bootstrapper

Job: Reads your app and existing documents to understand what the project does. Then writes a description of the app and a first draft of what needs to be tested. Nothing else.

When to use: The very first step on any new project or feature. Nothing runs before this.

Not allowed to: Write tests, helpers, or fixtures. Give a pass or fail decision.

How to start it
You: "Use project-bootstrapper to gather context for my-app.
      The app source is at /src and the product docs are in /docs/product"

Agent reads the app → writes docs/application-intelligence/my-app.md
                    → writes a first draft in evidence/requirements.json
● Can read and write files ● Model: Sonnet
DISCOVER playwright-cli

Job: Opens the real app in a browser and finds the buttons, fields, and page addresses that tests will need. Saves those as named constants in the config files.

When to use: After project-bootstrapper finishes, before any tests are written. Use it to verify that selectors actually work in the browser.

Not allowed to: Write tests. Give a pass or fail decision.

What it produces
You: "Use playwright-cli to find the selectors for the login page at /login"

Agent opens the browser → inspects the page → writes:
// playwright/configs/ui/auth.selectors.ts
export const EMAIL_INPUT    = '[data-testid="email"]';
export const PASSWORD_INPUT = '[data-testid="password"]';
export const LOGIN_BTN      = '[data-testid="login-btn"]';
● Can read files and run browser commands ● Model: Sonnet
BUILD playwright-test-automation

Job: Takes one approved requirement and turns it into real test code — config constants, helper steps, and the test file.

When to use: Only after you mark a requirement active in evidence/requirements.json. One requirement per session.

Not allowed to: Approve its own work. Write more than one requirement at a time.

What it writes for requirement LOGIN-001
playwright/configs/ui/auth.selectors.ts   ← selectors (if not already there)
playwright/configs/app/routes.ts           ← /login route constant
playwright/support/helpers/auth.helper.ts ← loginAs(email, password) step
playwright/tests/auth/login.spec.ts       ← the actual test

// login.spec.ts (simplified)
test('[LOGIN-001] logs in with valid credentials', async ({ authHelper }) => {
  await authHelper.loginAs('user@example.com', 'secret');
  await expect(page).toHaveURL('/dashboard');
});
● Can read and write files ● Model: Sonnet
EVALUATE pre-merge-qa-gate

Job: The independent reviewer. Reads the test files and the results of the test run, scores each test out of 100, and gives one verdict: PASS, PASS WITH NOTES, or BLOCK.

When to use: After the test is written and you have the test run output and lint output ready.

Not allowed to: Edit any files. Run any commands. Fix problems itself. It is read-only.

How to call it
You: "Use pre-merge-qa-gate to evaluate my changes.
      Here is the diff: [paste diff]
      Here is npm test output: [paste output]
      Here is npm run lint output: [paste output]"

Gate reviews → returns:
  LOGIN-001: 90/100 — PASS
  Overall verdict: PASS
  No blockers found.

Points taken off per problem found:

Problem found in the testPoints off
Test name is unclear or wrong−15
Test type or priority is wrong−15
Test depends on another test to run first−20
The check at the end is weak or missing−20
Code is copied from another test−10
Errors are being hidden (bad try/catch)−20
Test creates data but does not clean it up−15
No link back to a requirement−5
Used a CSS selector when a better option existed−10
Used a position (1st, 2nd) instead of a name filter−10

80 points or more is needed to pass. A broken hard rule blocks the merge even if the score is 100.

● Read-only — cannot save files ● Model: Opus
DIAGNOSE playwright-bug-hunter

Job: When a test is failing, this agent reads the failure, works out why it happened, and proposes a small, targeted fix.

When to use: When a test is failing and you want to know the real reason, not just a guess.

Not allowed to: Run tests speculatively. Score its own fix.

How to call it
You: "Use playwright-bug-hunter. This test is failing in CI.
      Error: Timeout 30000ms exceeded waiting for [data-testid='submit-btn']"

Agent reads the test → checks the selector → checks the page →
Root cause: The button is inside a dialog that only appears after an API call.
            The test did not wait for the API response before looking for the button.
Fix: await page.waitForResponse('**/api/cart'); before clicking.
● Can read, search, and edit files ● Model: Opus
SHIP pr-creator

Job: Opens a pull request for you. Looks at all commits on your branch, writes a title, a summary of changes, and a test checklist — following the repo's standard format.

When to use: Once the QA gate gives a PASS and you are ready to send the code for review.

What it creates
Title: feat(auth): add login test for LOGIN-001

Summary:
- Adds loginAs() helper to auth.helper.ts
- Adds login.spec.ts covering the happy-path login flow
- Selectors added to auth.selectors.ts

Test plan:
☐ npm test passes locally
☐ QA gate verdict: PASS (score 90/100)
● Can read files and run git commands ● Model: Sonnet
MAINTAIN workflow-maintainer

Job: Keeps the harness itself clean. If a script, agent file, or document seems duplicated or unused, this agent helps you decide what to keep and what to remove.

When to use: When the harness feels messy, or when you want to simplify docs or scripts.

Example conversation
You: "Use workflow-maintainer. We have two files that seem to do the same thing:
      scripts/check-rules.mjs and .claude/hooks/validate-playwright-rules.mjs"

Agent reads both → compares them →
"check-rules.mjs is a thin wrapper that calls validate-playwright-rules.mjs.
 It adds no logic of its own. Safe to delete check-rules.mjs and update
 any npm scripts that reference it."
● Can read and edit harness files ● Model: Sonnet

Rules

Simple definition

A rule is something the harness checks every time a file is saved. There are two kinds. Hard rules stop the file from saving if they are broken. Soft rules are checked later by the QA reviewer, who takes off points — if the score drops below 80, the merge is blocked.

You do not configure rules per project. They are inherited automatically. The hooks check hard rules when you save; the QA gate checks soft rules when you ask for a review.

Hard rules — the file will not save if these are broken

no-hard-waitBlocking
Why this rule existsTelling a test to "wait 5 seconds" is a guess. If the page loads slower one day, the test fails. If it loads faster, the test wastes time. The test should wait for a real signal instead.
Do not writepage.waitForTimeout(5000)
Write insteadWait for something real — a network call or a visible element
Wrong
await page.click('#submit');
await page.waitForTimeout(3000); // hoping the page loaded
await expect(page.locator('.success')).toBeVisible();
Right
await page.click('#submit');
await page.waitForResponse('**/api/orders'); // wait for the real signal
await expect(page.locator('.success')).toBeVisible();
no-hardcoded-selectorBlocking
Why this rule existsIf you write a button's test-id directly in a test, and the developer renames it, you have to search and update every test that mentions it. One config file means one fix.
Do not writea selector string directly in a test or helper
Write insteada named constant from the config files
Wrong
await page.click('[data-testid="checkout-btn"]'); // hardcoded
Right
import { CHECKOUT_BTN } from '../configs/ui/cart.selectors';
await page.click(CHECKOUT_BTN);
no-hardcoded-routeBlocking
Why this rule existsIf the URL or API address changes, every test that has it written directly will break. One config file means one place to update.
Do not writea URL or API path directly in a test or helper
Write insteada named constant from the routes config file
Wrong
await page.goto('/dashboard/settings'); // hardcoded URL
Right
import { ROUTES } from '../configs/app/routes';
await page.goto(ROUTES.SETTINGS);
no-page-objectBlocking
Why this rule existsThe harness already has configs (for selectors) and helpers (for steps). A page object class does the same job and creates confusion about which file owns what.
Do not writea class that wraps page actions
Write insteada plain function in the helpers folder
Wrong — page object class
class LoginPage {           // ❌ not allowed
  async login(email, password) {
    await this.page.fill('#email', email);
    await this.page.click('#submit');
  }
}
Right — plain helper function
// playwright/support/helpers/auth.helper.ts
export async function loginAs(page, email, password) {
  await page.fill(EMAIL_INPUT, email);
  await page.fill(PASSWORD_INPUT, password);
  await page.click(LOGIN_BTN);
}
no-credential-literalBlocking
Why this rule existsA password written in a file gets saved to git history forever, even if deleted later. Anyone who ever clones the repo can find it.
Do not writea password, API key, or token as plain text
Write insteadread from an environment variable
Wrong
await loginAs('admin@example.com', 'SuperSecret123'); // ❌ literal password
Right
// .env (gitignored file)
TEST_PASSWORD=SuperSecret123

// In the test:
await loginAs('admin@example.com', process.env.TEST_PASSWORD);
storage-state-authBlocking
Why this rule existsIf every test logs in before it runs, the whole suite gets slow and breaks whenever the login page changes. Log in once, save the session, and share it.
Do not writea login flow inside beforeEach()
Write insteada storageState setup project that logs in once
Wrong — logs in before every test
beforeEach(async ({ page }) => {
  await page.goto('/login');         // ❌ repeated every test
  await page.fill('#email', '...');
  await page.click('#submit');
});
Right — login once, reuse the saved session
// playwright.config.ts projects: [ { name: 'setup', testMatch: '**/auth.setup.ts' }, { name: 'tests', dependencies: ['setup'], use: { storageState: '.auth/user.json' } } ]
base-fixture-importBlocking
Why this rule existsThe base fixture is the single place that gives tests access to helpers. Importing directly from Playwright bypasses helpers and breaks the whole chain.
Do not writeimport { test } from '@playwright/test' in a test file
Write insteadimport from the base fixture
Wrong
import { test, expect } from '@playwright/test'; // ❌ bypasses the fixture
Right
import { test, expect } from '../fixtures/base.fixture'; // ✅ correct
smoke-read-onlyBlocking
Why this rule existsA smoke test should be safe to run against a live or shared environment at any time. If it creates or deletes data, it could break something real.
Do not writePOST, PUT, PATCH, or DELETE requests in a @smoke test
Write insteadread-only checks only; put data changes in an @e2e test
Wrong — smoke test that creates an order
test('[ORDER-001] creates order', { tag: ['@smoke'] }, async ({ request }) => { const res = await request.post('/api/orders', { ... }); // ❌ write in smoke });
Right — smoke test only reads
test('[ORDER-001] shows order list', { tag: ['@smoke'] }, async ({ page }) => { await page.goto(ROUTES.ORDERS); await expect(page.getByRole('table')).toBeVisible(); // ✅ read-only });
no-sql-literalBlocking
Why this rule existsA SQL query written directly in a test is tied to the current database. If a table is renamed, you have to update every test that mentions it. One config file means one update.
Do not writea SQL query string in a test or helper
Write insteada saved query from the db config, passed to the db helper
Wrong
const rows = await db.query("SELECT * FROM users WHERE email = $1"); // ❌
Right
// playwright/configs/db/user.queries.ts export const GET_USER_BY_EMAIL = 'SELECT * FROM users WHERE email = $1'; // In the helper: import { GET_USER_BY_EMAIL } from '../configs/db/user.queries'; const rows = await db.query(GET_USER_BY_EMAIL, [email]);
focused-or-quarantined-testBlocking
Why this rule existstest.only() makes only that one test run and hides all failures from the rest of the suite in CI. A skipped test with no explanation hides a problem with no one responsible for fixing it.
Do not writetest.only() or a skip with no explanation
Write insteadadd a quarantine comment above any skip or fixme
Wrong
test.only('[LOGIN-001] logs in', async () => { ... }); // ❌ hides other failures test.skip('[CART-002] adds to cart', async () => { ... }); // ❌ no explanation
Right
// @quarantine CART-BUG-45: cart API returning 500 in staging, fix in progress test.fixme('[CART-002] adds to cart', async () => { ... });
one-requirement-tagBlocking
Why this rule existsEvery test must be linked to exactly one requirement. No link means the test is orphaned. Two links means the coverage report is confusing. An unknown ID means the link points to nothing.
Do not writea test with no ID, two IDs, or an unknown ID
Write insteadexactly one known ID in the title and as a tag
Wrong — no requirement link
test('user can log in', async () => { ... }); // ❌ no ID, no tags
Right — one ID, correct tags
test('[LOGIN-001] logs in with valid credentials', { tag: ['@LOGIN-001', '@smoke', '@P0'] }, async ({ authHelper }) => { ... } );

Soft rules — no file is blocked, but points are deducted

These rules are not checked when you save. The QA gate reviewer checks them when you ask for a pull request review. Each problem reduces the test score. Below 80 means the pull request is blocked.

locator-priorityGraded
Why this rule existsSome ways of finding a button are more stable. Finding it by its visible label survives a code change. Finding it by a CSS class breaks the moment the class is renamed.
Preferred order — best to worst 1. getByRole() — what the element is (button, link, heading)
2. getByLabel() — the label next to a form field
3. getByText() — visible text on screen
4. getByTestId() — a data-testid the developer added
5. CSS / XPath — only as a last choice, with a written reason
Lower priority — CSS selector (fragile)
await page.locator('.btn-primary.submit').click(); // breaks if class name changes
Higher priority — by role and name (stable)
await page.getByRole('button', { name: 'Submit order' }).click();
narrow-before-indexGraded
Why this rule existsIf you find the "second button on the page" and someone adds a new button above it, your test silently starts checking the wrong button. It still passes but proves nothing.
Do not write.first() or .nth(1) when the element has a unique label
Write insteadnarrow down by content first
Wrong — position-based (fragile)
await page.getByRole('button').nth(1).click(); // which button is "second"?
Right — filter by name (stable)
await page.getByRole('button').filter({ hasText: 'Add to cart' }).click();
search-before-createGraded
Why this rule existsThe same selector or page address might already be saved in a config file. Two copies of the same thing means when the app changes, you have to update both.
The ruleBefore creating any new config, helper, or test — search for the exact text value across playwright/configs/** and playwright/support/helpers/**. If you find it anywhere, use the existing one.
How to search before creating
# Search for the selector value before adding it to a new file grep -r 'data-testid="checkout-btn"' playwright/configs/ playwright/support/ # If the search finds something → use that existing constant # If the search finds nothing → then it's OK to create a new one
